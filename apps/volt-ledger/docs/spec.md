# VOLT Ledger Brain: specification

Status: approved 24 Nov 2026 (separate Render service chosen); ratio catalogue expanded the same day. Date: 24 Nov 2026. Companion to `intent.md`.
No application code is written until this spec is approved.

Assumption ids (A1 to A9) refer to the Phase 0 Discovery Memo. New assumptions in this spec start at A10.

## 1. Where it runs

The brain is a Python service, `apps/volt-ledger`, inside VOLT-Main. People use it only through the VOLT Console
(`apps/volt-console`), which is already deployed on Render from `render.yaml`.

```
Browser (VOLT Console UI)
   |  upload TB / statements, chat, review queue
   v
volt-console  (Render web service, Node, existing)
   |  Claude tool loop: the model calls ledger_* tools
   |  HTTP on Render's private network, shared secret
   v
volt-ledger   (Render private service, Python, new)
   |  deterministic tools, ontology, proposal ledger, evidence ledger, verification gate
   v
SQLite on a Render persistent disk (volt-ledger-data)
```

- **volt-ledger** is a Render *private service* (`type: pserv`): not reachable from the internet, only from the
  console. It is added to the same `render.yaml` blueprint, with its own 1 GB disk.
- **The console** gets new `ledger_*` tools in `server/tools.ts`. Each one validates input with Zod, then forwards
  the call to volt-ledger over HTTP. The console never computes ledger numbers itself.
- **Secrets:** `VOLT_LEDGER_TOKEN` is generated by Render and given to both services; every call from the console
  carries it. `VOLT_LEDGER_URL` points the console at the private service.
- **Local run:** both services start on a laptop (`uvicorn` for the ledger, `npm run dev` for the console), and the
  console runs in demo mode without Claude credentials.
- [ASSUMPTION A10] A second Render service is acceptable. It adds one more service to the bill (a starter instance
  plus a 1 GB disk) [UNVERIFIED: current Render pricing].
- [ASSUMPTION A11] Python 3.12, FastAPI for HTTP, SQLite for storage, `pytest` and `hypothesis` for tests.
  SQLite is enough for one engagement at a time; Postgres is a later swap behind the same storage interface.

**Money rule across the wire.** JavaScript turns JSON numbers into floating point, so every amount crosses the
HTTP boundary as a **string of integer minor units** (cents), for example `"125000099"`, together with an ISO
currency code. Rates and ratios cross as decimal strings, for example `"0.0425"`. The console passes them through
untouched.

## 2. System layers

| # | Layer | Lives in | Job |
|---|---|---|---|
| 1 | Ingress and identity | console | Sign-in (existing `VOLT_ACCESS_TOKEN`), file upload, engagement and user id on every call |
| 2 | Planner and orchestration | console (Claude) | Decides which tools to call, in what order, and writes the explanation |
| 3 | Deterministic tool layer | volt-ledger | Every parse, balance, mapping record, journal, ratio and allocation |
| 4 | Ontology and knowledge graph | volt-ledger | Elements and associations, XBRL-labelled, multi-GAAP |
| 5 | Evidence ledger | volt-ledger | Append-only record of every tool call, source and result |
| 6 | Verification and policy gate | volt-ledger | Checks every draft output before it can leave; holds the review queue |
| 7 | Output | console | Statements, gap report, proposed journals, allocation results, narrative, downloads |

Rule for layer 2: the model may only quote a number that appears in an evidence record. Layer 6 enforces it.

## 3. Data model

All tables are append-only except `review_decision` state, which is itself recorded as new rows. Nothing is ever
updated in place or deleted. Every row carries `engagement_id` and `created_at` (UTC).

### 3.1 Element (one table for every node in the ontology)

| Column | Type | Notes |
|---|---|---|
| element_id | text, PK | Canonical id, e.g. `canon:InterestIncome` |
| element_type | text | `concept`, `account`, `line_item`, `dimension`, `member`, `policy_gap`, `standard_paragraph` |
| label | text | Plain-language label |
| xbrl_qname | text, nullable | e.g. `ifrs-full:RevenueFromInterest`, `us-gaap:InterestAndDividendIncomeOperating`. Null only when no standard term exists, and then `traits.no_standard_term = true` with a reason |
| balance_type | text, nullable | `debit` or `credit` (for monetary concepts) |
| period_type | text, nullable | `instant` or `duration` |
| traits | JSON | Free attributes, e.g. `{"gaap": ["ifrs"], "monetary": true}` |
| provenance | JSON | Where the element came from: `{"source": "ifrs-full taxonomy 2025", "added_by": "loader"}` or `{"source": "client_tb", "doc_id": "...", "row": 42}` |

Every client account becomes an `account` element; every canonical reporting idea is a `concept` element.

### 3.2 Association (edges between elements)

| Column | Type | Notes |
|---|---|---|
| association_id | text, PK | |
| from_element | text, FK | |
| to_element | text, FK | |
| association_type | text | `presentation`, `calculation`, `mapping`, `reconciliation_path`, `cites`, `gap_of` |
| gaap | text, nullable | `ifrs`, `us-gaap`, `local:<code>`, or null when GAAP-neutral |
| weight | text, nullable | Decimal string, for calculation arcs (`"1"` or `"-1"`) |
| order | integer, nullable | Presentation order |
| confidence | text, nullable | Decimal string 0 to 1, for `mapping` arcs proposed by the model |
| evidence_id | text, FK | The evidence record that created this edge |

One economic event maps to **one** canonical concept. US GAAP and IFRS differences are separate `presentation`
arcs from that same concept, never duplicate concepts.

### 3.3 Proposal ledger (journals)

`journal_entry`

| Column | Type | Notes |
|---|---|---|
| journal_id | text, PK | |
| idempotency_key | text, unique | Same key twice returns the first journal, never a second one |
| period | text | `YYYY-MM` |
| status | text | `proposed` only in v1 (the brain never posts to a client GL) |
| kind | text | `adjustment`, `allocation`, `reclass`, `reversal` |
| reverses_journal_id | text, nullable | Set only on reversals |
| description | text | |
| evidence_id | text, FK | |

`journal_line`

| Column | Type | Notes |
|---|---|---|
| line_id | text, PK | |
| journal_id | text, FK | |
| account_element_id | text, FK | Must be an `account` element |
| dimensions | JSON | e.g. `{"business_line": "retail", "cost_centre": "IT01"}` |
| debit_minor | integer | >= 0 |
| credit_minor | integer | >= 0; exactly one of debit or credit is above zero |
| currency | text | ISO 4217 |

`period_lock`: `period`, `locked_at`, `locked_by`. No journal may be written into a locked period.

### 3.4 Source documents and trial balance

`source_document`: `doc_id`, `kind` (`trial_balance`, `financial_statements`), `filename`, `sha256`,
`uploaded_by`. `tb_row`: `doc_id`, `row_number`, `account_code`, `account_name`, `debit_minor`, `credit_minor`,
`currency`, `period`, raw text of the row. `fs_cell`: `doc_id`, `page`, `table_index`, `row_label`, `column_label`,
`value_minor`, raw text.

### 3.5 Driver values (non-GL inputs)

`driver_value`: `value_id`, `kind` (`plan`, `driver`, `reg`, `market`), `key` (e.g. `fte`, `rwa`, `cet1_capital`,
`shares_outstanding`, `share_price`), `period`, `dimensions` (JSON), `value` (decimal string, or minor units for
money), `unit`, `source` (`{doc_id, row}` or `{user}`), `evidence_id`. Append-only like everything else.

`metric_definition`: `metric_id`, `version`, `label`, `formula` (over concept ids and driver keys), `unit`,
`rounding`, `audiences`, `client_override_of` (nullable), `reason`. The default rows come from
`ratio-catalogue.md`.

### 3.6 Evidence record

| Column | Type | Notes |
|---|---|---|
| evidence_id | text, PK | `E000123` |
| tool | text | Tool name |
| inputs | JSON | Exactly what the tool received |
| outputs | JSON | Exactly what it returned |
| sources | JSON | List of `{doc_id, row}` or `{doc_id, page, table}` or `{element_id}` or `{evidence_id}` |
| code_version | text | Git commit of volt-ledger |
| actor | text | `model`, `user:<id>`, or `system` |
| prev_hash, hash | text | SHA-256 chain, so any edit to history is detectable |

### 3.7 Review queue

`review_item`: `item_id`, `kind` (`mapping`, `policy_determination`, `policy_gap`, `journal`, `allocation`,
`narrative`), `ref_id`, `reason` (e.g. `confidence_below_0.90`, `first_client_run`, `always_review`).
`review_decision`: `item_id`, `stage` (`engagement_lead`, `client`), `decision` (`approve`, `reject`, `amend`),
`by`, `note`, `evidence_id`. An item reaches the client view only after `engagement_lead` approval, and is
released only after `client` approval.

## 4. Tool definitions

Every tool writes one evidence record and returns its `evidence_id`. Every tool is deterministic: same inputs and
same data give the same outputs.

| Tool | Inputs | Outputs | Invariants |
|---|---|---|---|
| `ingest_trial_balance` | upload id, column mapping, period, currency | `doc_id`, row count, total debits, total credits, rejected rows with reasons | Every input row is either stored or listed as rejected; stored rows + rejected rows = input rows; amounts parsed to integer minor units with no float step; reports whether debits equal credits |
| `extract_statement_tables` | upload id (PDF) | list of tables with page, index, cells | Every cell keeps page and table reference; values parsed to minor units; unparseable cells kept as text, flagged |
| `tie_out` | `doc_id` of TB, `doc_id` of statements, mapping set | per statement line: TB-derived total, statement value, difference | Difference computed in integer minor units; any non-zero difference is a failure, not a warning |
| `get_ontology_context` | element id or search text, GAAP | element, parents, children, mapping candidates | Read-only |
| `map_line_item_to_element` | `account` element id, target concept id, confidence, rationale | `association_id` | Target must exist and be a `concept`; confidence below 0.90, or first client run, creates a review item; never overwrites an earlier mapping, adds a new one that supersedes it |
| `flag_policy_gap` | account or concept id, gap type, standard reference, rationale | gap element id, review item id | Always creates a review item; standard reference is stored as [UNVERIFIED] unless a `standard_paragraph` element backs it |
| `retrieve_standard_paragraph` | standard (e.g. `IFRS 15`), paragraph, or a concept id | element(s) with reference and, in v1, no text | Never returns text the store does not hold; returns `not_found` rather than a guess |
| `propose_journal_entry` | idempotency key, period, kind, lines, description | `journal_id` | The single write path to the proposal ledger; total debits = total credits; each line has exactly one non-zero side; accounts exist; period not locked; same idempotency key returns the original journal |
| `reverse_journal_entry` | journal id, period, reason | reversal `journal_id` | Swaps debit and credit on every line; after it, balances for every account and dimension equal those before the original |
| `get_balances` | period, account or concept ids, dimensions, include proposals yes or no | balances in minor units | Balance = TB balance + sum of included proposal lines; read-only |
| `compute_ratio` | metric id from the metric registry (`ratio-catalogue.md`), period, optional dimension filter (e.g. business line) | value as decimal string, every input with its evidence id, the definition used | Uses only `get_balances` results and stored `driver_value` rows; Decimal arithmetic with the registry's rounding rule; a missing input returns `not_computable` with the list of missing inputs; denominator zero returns an error |
| `record_driver_values` | upload id or typed values, kind (`plan`, `driver`, `reg`, `market`), period | stored `driver_value` ids | Every value has a source (upload row or the person who typed it); the model cannot call it with values of its own |
| `run_allocation` | pool (account and cost centre), basis (`fte`, `transaction_count`, `balance`, `rwa`), driver values per target, period | per-target amounts, proposed allocation journal id | Allocated amounts sum exactly to the pool; rounding by largest remainder, method recorded; driver values come from an upload or user entry with evidence, never from the model |
| `check_output` | draft narrative and the evidence ids it relies on | pass or fail, list of problems | The verification gate (section 6) |
| `record_review_decision` | item id, stage, decision, note | decision id | Client stage needs a prior engagement-lead approval |

The model can call every tool except `record_review_decision`, which only a signed-in person can call from the
review screen.

## 5. LLM boundary

**The model does:**

- Choose which tools to call and in what order.
- Propose mappings from accounts to concepts, with a confidence score and a short rationale.
- Read policy notes in the statements and propose policy determinations, citing the page.
- Propose policy gaps and the standard they relate to.
- Propose allocation bases and journal lines for a person to review.
- Write the narrative, quoting only numbers that tools returned.

**Prohibited operations (the model must never):**

1. Do arithmetic on amounts, including sums, differences, percentages and roundings, in its own text.
2. State a number that is not in an evidence record of the current engagement.
3. Write to the proposal ledger other than through `propose_journal_entry` or `reverse_journal_entry`.
4. Change or delete any stored record, mapping or evidence.
5. Invent a standard paragraph, quote standards text, or cite a paragraph without marking it [UNVERIFIED] when no
   `standard_paragraph` element backs it.
6. Invent driver values (FTEs, transaction counts, RWA) for an allocation.
7. Approve its own output or call `record_review_decision`.
8. Create ad-hoc account categories when an XBRL term exists.

## 6. Verification and policy gate

`check_output` runs on every draft before the console shows it, and fails the draft if:

- **G1 numbers:** any number in the text does not match a value in a cited evidence record (exact string match on
  the formatted value).
- **G2 citations:** any sentence that states a policy, a standard requirement or a figure has no citation key.
- **G3 standards:** any standard citation lacks either a `standard_paragraph` element or an [UNVERIFIED] tag.
- **G4 balance:** any referenced journal does not balance (rechecked, not trusted).
- **G5 tie-out:** any statement shown has a non-zero tie-out difference.
- **G6 coverage:** any trial-balance row is neither mapped nor flagged as unmapped.

A failed draft goes back to the model once with the problems; a second failure is shown to the engagement lead as
failed, with the problems, and never to the client.

## 7. Validation rules (how we prove the spec holds)

| Rule | Test |
|---|---|
| Every TB row is accounted for | Ingest test files with good, malformed and duplicate rows; assert stored + rejected = input |
| Every mapping is traceable | For each mapping association, follow `evidence_id` to the source `tb_row`; assert none is missing |
| Every journal balances | Property-based test: random journals; unbalanced ones always raise, balanced ones always store |
| Reversals restore state | Property-based test: balances before = balances after original + reversal |
| Period locks hold | Property-based test: no journal can be written into a locked period |
| Idempotency | Same key twice gives one journal |
| Allocations tie | Property-based test: random pools and drivers; allocated sum = pool exactly |
| No floats for money | Code check in CI: no `float` on any money path; JSON amounts are strings |
| Every narrative claim is backed | Gate G1 and G2 on a fixed set of good and bad sample narratives |
| Evidence is tamper-evident | Edit one stored record in a test copy; assert the hash chain check fails |

## 8. Review and approval flow

1. The model produces outputs; each lands in the review queue (A9: policy determinations, policy gaps, journals,
   allocations, client-facing narrative, and mappings below 0.90 or from the first client run).
2. The engagement lead reviews in the console and approves, rejects or amends.
3. Only approved items appear in the client view; the client controller gives final sign-off.
4. Every decision is an evidence record.

## 9. Open decisions for approval

1. **A10:** volt-ledger as a second Render service (private, with its own disk). The alternative is to put Python in
   the console's Docker image, which saves a service but makes the image and start-up more complex. I recommend the
   separate private service.
2. **A11:** Python 3.12, FastAPI, SQLite, pytest and hypothesis.
3. Ratio list: the full catalogue in `ratio-catalogue.md` (about 70 metrics grouped by audience: investors and IR,
   CFO, FP&A, business lines). The v1 demo computes every metric whose inputs the synthetic data contains.
